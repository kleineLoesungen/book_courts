`config.php` exposes:
```php
function load_env_config(): void;   // reads .env, throws RuntimeException if missing/invalid,
                                     // populates globals: $DB_HOST, $DB_PORT, $DB_NAME, $DB_USER, $DB_PASS, $dsn
```

`.env` format (from Plan 01-01), holds the five keys used to connect:
```ini
DB_HOST=...
DB_PORT=...
DB_NAME=...
DB_USER=...
DB_PASS=...        ; quoted if it contains ; " \ or whitespace/non-ASCII
```

The PostgreSQL role name to rotate is whatever `DB_USER` currently resolves to in `.env` — read it programmatically (never copy it into a plan/commit), e.g.:
```bash
php -r "chdir(__DIR__); \$c = parse_ini_file('.env', false, INI_SCANNER_NORMAL); echo \$c['DB_USER'] . PHP_EOL;"
```

  <how-to-verify>
Follow this runbook exactly, as ONE coordinated maintenance action (per D-02 — do not split the Postgres change and the .env deployment into separate, hours-apart steps; the app will 500 on every request between the two):

1. Generate a new strong password using ONLY letters and digits (this deliberately avoids the `;`/`"`/`\`/whitespace INI-quoting pitfalls that `.env`'s `parse_ini_file()` parsing has):
   ```bash
   openssl rand -base64 24 | tr -dc 'A-Za-z0-9' | cut -c1-24
   ```
   Run this in your own terminal. Do not paste the result into any file that gets committed to git, into this plan, into a commit message, or into chat — use it directly in steps 3 and 4 below and nowhere else.

2. Identify the PostgreSQL role name to rotate — it's the current `DB_USER` value in this repo's `.env` (migrated there by Plan 01-01). Read it yourself, e.g.:
   ```bash
   php -r "chdir(__DIR__); \$c = parse_ini_file('.env', false, INI_SCANNER_NORMAL); echo \$c['DB_USER'] . PHP_EOL;"
   ```

3. Connect to the production PostgreSQL server with an ADMIN/superuser credential (hosting provider's DB console, or `psql` if you have admin access) and run:
   ```sql
   ALTER ROLE <DB_USER_FROM_STEP_2> WITH PASSWORD '<NEW_PASSWORD_FROM_STEP_1>';
   ```
   Substitute the real values — never write the literal new password into any script, commit, or planning file.

4. IMMEDIATELY (same maintenance window — this is the critical part D-02/PITFALLS.md calls out) update `DB_PASS` in the **local** `.env` in this repo to the same new password, then deploy/sync it to production using your existing file-based deployment method (FTP/SFTP/hosting file manager) — this project has no git-push-to-deploy pipeline, so the production `.env` must be updated the same way `conf.php` was updated historically. Since the new password is alphanumeric-only (step 1), it does NOT need quoting in `.env`. Preserve `chmod 600` on both the local and deployed copies.

5. Health check: visit the LIVE production site and complete a real, authenticated action that requires a database round trip (not just a static page load) — log in as a member on `index.php` and view the week/day booking view, AND log in as an admin on `admin.php` and view the bookings list. Both must succeed.

6. If the health check fails: immediately revert `.env`'s `DB_PASS` (local and deployed) back to the password that was in place before step 3 — the app will otherwise fail every request until the two systems match again. Only investigate after reverting.

7. This is a single-role rotation (no old/new dual-role window per D-02) — once step 5 passes, the old password is already fully invalid on the PostgreSQL server; there is no separate "old role" to revoke afterward.
